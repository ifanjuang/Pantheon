# Hermes Profiles

Hermes profiles are runtime-boundary templates for external Hermes execution.

Canonical Pantheon Role definitions remain in:

```text
docs/governance/AGENTS.md
```

A profile is not a Pantheon Role, and Pantheon Role coverage does not require a
matching profile.

Shared adapter notes may live at the root of `hermes/profiles/` when they
coordinate profile use without creating executable configuration.

No profile folder is a canonical governance source.
No profile folder is automatically installed into Hermes.
No profile may approve, canonize, promote memory, mutate doctrine or merge code.

## Profile cardinality rule

Pantheon currently has eight canonical governance Roles.

The normal governed runtime path is the `pantheon-governed` envelope. A separate
profile is justified only by a demonstrated runtime boundary, such as a materially
different model, memory posture, credential set, capability surface, data-exposure
posture or execution-isolation requirement.

```text
Pantheon Role != Hermes Profile
Role coverage != profile cardinality
posture changed != profile changed
cognitive function != runtime boundary
```

A different planning, investigation, production, critique, evidence, risk,
readiness, formulation or arbitration function should normally be expressed
through a posture, Method, Skill, Capability or bounded delegation inside the
governed runtime rather than by creating a profile.

## Role-aligned profile retirement

The historical Role-mirrored Hermes profile folders for APOLLO, ARGOS, ATHENA,
HEPHAISTOS, IRIS, THEMIS and ZEUS have been retired.

Their audit found no materially distinct model, memory posture, credential set,
capability surface, data-exposure posture or execution-isolation requirement.
Their `profile.yaml` and `soul.md` files only restated candidate-output classes,
approval ceilings and Role responsibilities already owned by Pantheon governance
and the governed Hermes method.

No replacement profile family is created.

```text
retired Role mirror != retired governance Role
profile shell removed != capability removed
Role viewpoint needed != profile needed
```

Useful work remains available through the governed runtime envelope plus the
appropriate posture, Method, Skill, Capability or bounded delegation.

No `mnemosyne-agent` profile is required. The same rule applies to every Pantheon
Role: governance jurisdiction alone never creates runtime identity.

If a future requirement demonstrates a real runtime boundary, a profile may be
introduced for that boundary. It must not be introduced merely to mirror a Role,
work posture or cognitive function.

## Governed runtime envelope

For normal professional governed work, use the `pantheon-governed` runtime
envelope defined by the admitted Hermes template and the profile constitution.

The runtime envelope controls material execution conditions such as memory,
credentials, capability surface, model/provider exposure and isolation. The
governed method selects the work posture and the smallest sufficient runtime
mechanism.

```text
pantheon-governed runtime envelope
+ admitted Task Contract
+ qualified observable runtime capability surface
+ posture / Method / Skill selected for the work
= candidate execution posture
```

`pantheon-governed` is not a Pantheon Role.

`default` may remain the sticky CLI/UI profile depending on the deployed Hermes
surface. Governed work must use the admitted governed route for a new session;
prompt content alone does not prove or switch runtime profile state.

`tool_search:` may discover an available capability inside the selected runtime,
but it is not a profile router. An old session retains its frozen system prompt;
changing the active profile affects only a newly created session.

Inside an admitted Task Contract, Hermes may choose among qualified runtime
mechanisms that satisfy the same objective and constraints.

```text
Task Contract constrains legitimacy
Hermes selects execution means
runtime mechanism may change
boundary must not change silently
```

A different tool, skill, plugin, MCP connection or delegation mechanism does not
require a new profile when it stays inside the same admitted scope,
data-exposure posture, effect ceiling, memory posture and approval boundary.

A materially different model does not automatically require a profile either; it
requires one only when the model choice changes the governed runtime boundary.

A mechanism that widens source access, private-data disclosure, credentials,
memory behavior, execution isolation or effect ceiling must return a Capability
Gap or request the applicable gate before use.

## Memory and authority baseline

The governed runtime keeps runtime memory inert by default unless a separately
qualified boundary admits it.

Baseline posture remains:

```text
external provider: off
built-in MEMORY.md injection: off
built-in USER.md profile injection: off
memory tool: off
X-Hermes-Session-Key: not sent
```

`hermes memory off` establishes only the external-provider state. It does not by
itself prove built-in injection or tool states.

`assistant-personal` is a separate non-governed runtime posture. It may use
user-selected memory behavior, but it must not receive Pantheon Task Contracts,
professional task authorization or canonical memory authority.

```text
runtime mode configured != task authorized
profile route reachable != profile safe
hermes memory off != built-in memory injection off
external provider absent from tool list != external memory proven off
memory tool absent != memory injection disabled
qualified capability != consequential effect authorized
runtime choice != governance decision
```

If the material runtime boundary cannot be observed sufficiently for the task,
the route remains `not_qualified` and must emit a Capability Gap.

## Adapter constitution

`PROFILE_CONSTITUTION.md` records the candidate runtime-profile constitution.

It is an adapter note only.

It does not create profiles, configure Hermes, route gateways, create Kanban
boards, authorize execution, approve outputs or promote memory.

## Read order

Before using or reviewing a governed Hermes profile or runtime route, read:

1. `docs/governance/AGENTS.md`
2. `docs/governance/HERMES_INTEGRATION.md`
3. `hermes/profiles/PROFILE_CONSTITUTION.md`
4. `hermes/profiles/_base/README.md`
5. `hermes/profiles/_base/base-soul-rules.md`
6. the admitted runtime template/configuration for the selected route
7. any profile-specific files only when a distinct profile is actually justified
