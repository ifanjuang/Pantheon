# Revit Adapter Engineering Conformance

Status: supporting implementation contract — documented non-implemented — subordinate to `../../docs/governance/REVIT_LOCAL_ADAPTER.md`.
Date: 2026-08-07.

This note records engineering constraints for a future Revit adapter implementation. It does not create capabilities, authorize writes, select a production repository or change any governance boundary.

The implementation patterns were reinforced by review of local agent-driven takeoff systems, including OpenTakeoff, where the human UI and agent surface share deterministic logic, refusals are explicit, provenance is centralized, and parity/conformance are tested against fixed fixtures. The reference implementation is not a Revit dependency and none of its runtime, tool registry or approval concepts are imported as authority.

```text
engineering pattern reused != external runtime dependency
operation implemented != capability admitted
local menu enabled != task authorized
transaction committed != result accepted
```

## 1. One operation registry

The future add-in should have one closed `RevitOperationRegistry` or equivalent source of operation metadata.

The same registry should drive, directly or by generated artifacts:

```text
local Revit menu exposure
capability manifest
Host Agent operation binding
typed request validation
operation documentation
conformance test enumeration
version-support declaration
```

The registry must not be generated by reflecting over the Revit API.

A minimal operation record should include:

```yaml
capability_id: building_model.write.change_type
operation_id: revit.element.change_type.v1
operation_version: 1
effect_class: write_model
warning_level: W3
supported_revit_versions:
  - "2027"
required_document_state: document_open
required_context:
  fresh_document: true
  exact_targets: true
  writable_targets: true
preflight_required: true
authorization_required: true
transaction_required: true
idempotency: exact_action_single_use
rollback_posture: transaction_or_group
result_contract: action_report.v1
```

Adding an operation without deciding these policies should fail development validation rather than inherit defaults silently.

## 2. One deterministic implementation behind human and agent entry points

A human button and a Hermes-triggered operation must not have independent business implementations.

Target shape:

```text
Revit panel button
        |
        +----> typed Revit operation ----> Revit API
        |
Hermes / Host Agent
```

Not:

```text
Revit panel -> implementation A
Hermes      -> implementation B
```

For example, `revit.rooms.snapshot.v1` should use the same operation implementation whether triggered from a local diagnostic UI or through an admitted Task Contract.

This does not mean that both entry points have equal authorization. The local human UI and the governed Hermes path may apply different admission gates before they reach the shared technical operation.

## 3. Operation request envelope

Every externally callable operation should receive a typed envelope containing enough correlation and freshness material to prevent accidental cross-document execution.

Recommended fields:

```text
request_id
action_id
operation_id + version
binding_id
instance_id
document_ref
snapshot/freshness token
Task Contract reference where applicable
Context Pack reference where applicable
exact target references
operation arguments
idempotency key
authorization reference for consequential actions
request/preflight digest where applicable
```

The add-in should reject unknown fields only where contract strictness requires it, but it must reject unknown operation ids and unsupported operation versions.

## 4. Technical outcome family

The add-in and Host Agent need more precision than `success | error`, without inventing a parallel WorkIssue lifecycle.

Recommended technical outcomes:

```text
success
withheld
refused
failed
cancelled
rolled_back
```

### `success`

The bounded technical operation completed according to its contract.

```text
success != accepted result
success != Evidence
```

### `withheld`

The operation found useful material but intentionally declined to produce the requested stronger result because a prerequisite or distinction remains unresolved.

Examples:

```text
a candidate host relation exists but multiple hosts remain plausible
a family/type-dependent action cannot be prepared because the required type is absent
a query finds linked-model targets but the operation is host-document-only
a quantity can be observed but a phase/option ambiguity prevents the requested comparison
```

A withheld result should carry enough information for Hermes or the user to resolve the blocker without repeating completed work.

### `refused`

The operation is not allowed or technically safe under the exact current request, for example stale context, document mismatch, missing authorization or forbidden effect.

### `failed`

Execution entered the operation but a technical failure prevented completion. The result must state whether any transaction opened, committed, rolled back or left Revit unchanged.

### `cancelled`

The user or host deliberately stopped the action before completion.

### `rolled_back`

The operation began a reversible write path and the final model state was restored through Revit transaction semantics or an explicit TransactionGroup rollback.

These outcomes are technical observations only. Hermes and pantheon-mvp map them into the owning task/run/result records.

## 5. Normalized result envelope

Every operation should return a bounded result envelope even when the internal Revit API call uses a different shape.

Recommended common fields:

```yaml
status: success | withheld | refused | failed | cancelled | rolled_back
operation_id: revit.element.change_type.v1
operation_version: 1
request_id: req-...
action_id: act-...
binding_id: ...
instance_id: ...
document_ref: ...
observed_at: ...
freshness_token_after: ...
warnings: []
refusal_or_withheld_reasons: []
created: []
modified: []
deleted: []
trace_refs: []
```

Operation-specific payloads remain typed separately. A large arbitrary bag of Revit objects should never be serialized as the generic result contract.

## 6. Central provenance policy

Every meaningful operation family must have an explicit provenance policy.

For observations, capture at least:

```text
binding/plugin/Revit version
document reference
snapshot/freshness token
operation id/version
view/selection/scope material used
ElementId/UniqueId locators where applicable
units and conversion method
warnings and limitations
observation time
```

For writes, capture additionally:

```text
Task Contract and authorization references
exact request/preflight digests
transaction name
before-state summary/digest where practical
after-state summary/digest where practical
created/modified/deleted ElementIds where available
Revit failures/warnings
rollback posture
```

A new mutation class without an explicit provenance policy should fail registry validation.

## 7. Preserve machine proposal before human correction

When Hermes proposes a classification, mapping or model change and a human changes it, the corrected value must not erase the original proposal.

Target record shape conceptually:

```text
proposed
-> exact machine proposal and rationale/source refs

reviewed
-> accepted/corrected value

correction
-> actor, timestamp, kind and optional reason
```

Examples include:

```text
proposed type P03 -> accepted type P04
proposed room mapping A -> accepted room mapping B
proposed parameter value X -> accepted value Y
```

This comparison material belongs to governed project/evaluation records outside the add-in. The plugin only returns enough exact technical material to make the distinction possible.

## 8. Deterministic correction rules

Repeated human corrections may later justify a deterministic project-scoped rule. They must not become a natural-language instruction that is re-prompted on every element.

Candidate lifecycle:

```text
repeated reviewed correction
-> Rule Candidate outside the add-in
-> human reviews predicate and scope
-> admitted deterministic rule
-> Hermes invokes bounded observation/proposal operations
-> outputs return as new candidates
```

The add-in may execute a deterministic local predicate only when it is represented by an admitted typed operation or exact parameters. It must not store an autonomous learning rule database or promote a rule itself.

```text
correction observed != rule admitted
rule admitted != model mutation authorized
```

## 9. Human/agent parity tests

For every operation exposed both locally and through the Host Agent, testing should prove that both entry points reach the same operation implementation.

Read-operation acceptance shape:

```text
fixture model + exact context
-> local diagnostic call
-> Result A

same fixture model + exact context
-> Host Agent typed call
-> Result B

A == B after removal of transport-only correlation fields
```

For write operations, parity should compare model effects rather than only response JSON:

```text
fixture before state
-> local operation
-> effect set A

fixture restored
-> Host Agent operation with exact authorization fixture
-> effect set B

A == B
unexpected effects == 0
```

This is distinct from permission parity: the test harness may supply explicit authorization material for the agent path while the local diagnostic harness uses a dedicated test mode.

## 10. Operation conformance suite

Every registered operation should have both positive and negative contract coverage.

Minimum read-operation cases:

```text
valid request
invalid schema
unknown operation version
no document
wrong document reference
stale freshness token
missing target
unsupported category/context
large result bounded by pagination or scope
failure leaves the Revit session usable
```

Additional write-operation cases:

```text
authorization absent
expired authorization
authorization digest mismatch
preflight digest mismatch
read-only document
worksharing ownership conflict
pinned/grouped/hosted constraint
linked-model write refusal
missing family/type
forbidden effect
idempotent replay / single-use conflict
transaction rollback
no silent save or sync
```

A refusal test passes only if the refused action commits no unintended model effect.

## 11. Revit fixture corpus

Unit tests over pure C# policy code are necessary but insufficient. The adapter needs a fixed Revit acceptance corpus.

The corpus should combine small synthetic RVT fixtures with safely anonymized representative architectural models and target Revit 2027 first.

Candidate fixture dimensions:

```text
rooms and room boundaries
doors and room connections
walls/hosts/openings
levels and phases
design options
worksets and ownership
pinned/grouped elements
families and types
compound materials
views/sheets/schedules
linked models
warnings
quantity schedules and direct API quantities
```

For each fixture, keep independent expected observations/effects rather than pinning every golden to the current implementation output.

Useful gates include:

```text
expected elements found / unexpected elements returned
relation precision/recall where applicable
quantity absolute and relative error
determinism across repeated reads
human/agent parity
unexpected write count == 0
rollback restores expected state
fixture-count guard to detect silent corpus shrinkage
```

Live Revit integration tests remain necessary because ExternalEvent, transaction and failure-processing semantics cannot be proven by pure mocks alone.

## 12. Snapshot and delta as first-class test surfaces

A snapshot should be treated as a bounded observation contract, not an arbitrary serialized copy of the RVT database.

For a fixed scope, tests should pin:

```text
what categories/parameters/relations are included
what is deliberately omitted
source units and normalized units
freshness identity
stable ordering/digest rules
pagination/bounds
```

A delta test should prove:

```text
unchanged model -> empty meaningful delta
one bounded edit -> only expected affected observations
type change -> affected instances represented correctly
phase/option change -> context difference explicit
stale snapshot -> comparison refused or clearly qualified
```

## 13. File-effect safety

Operations that export files must not silently destroy unrelated files.

A safe technical policy should distinguish:

```text
target absent
target recognized as prior Pantheon Revit output
target exists with unknown authorship
explicit exact overwrite request
```

Export success does not authorize publication, transmission, save or sync.

Model-save and synchronization remain separate high-effect capabilities and are outside ordinary export behavior.

## 14. Structured warning factors over opaque confidence

For exact Revit API observations, the adapter should return named technical factors instead of pretending that one scalar confidence value verifies the result.

Examples:

```text
document_match
freshness_match
targets_resolved_exactly
phase_context_known
design_option_context_known
worksharing_clear
linked_model_involved
group_constraint_present
host_constraint_present
type_available
rollback_available
```

Hermes may use these factors to prioritize review. They do not become professional certainty or Evidence automatically.

## 15. Operation granularity

Avoid both extremes:

```text
one generic execute_revit_api operation      -> too broad
one network tool per trivial API getter      -> too fragmented
```

Prefer bounded semantic operations that may group deterministic Revit calls internally.

Examples:

```text
revit.selection.snapshot.v1
-> selection ids + categories + types + selected parameters + bbox summaries

revit.rooms.snapshot.v1
-> rooms + boundaries + levels + phase + bounded door connections

revit.element.change_type.v1
-> exact targets + exact destination type + preflight + one transaction
```

Cross-source reasoning remains in Hermes, not inside these operations.

## 16. Generated artifacts from the registry

To prevent three divergent registries — plugin menu, Pantheon capability mapping and Hermes tool schemas — the implementation should generate or verify derivative surfaces from one canonical operation registry.

Candidate derived artifacts:

```text
add-in capability manifest
local advanced-menu entries
Host Agent dispatch map
JSON/schema descriptors
Hermes binding metadata
documentation tables
conformance-test inventory
```

Generated output is not executable merely because it was generated. Code review and build/adoption gates remain separate.

## 17. Forbidden engineering shortcuts

The implementation must refuse these shortcuts even if they reduce early development effort:

```text
reflection over arbitrary Revit API methods
execute C# from agent-provided source
execute Python inside Revit from agent-provided source
generic invoke_method / eval surfaces
one mutable global approval flag
background silent write loop
agent-side save or sync after successful transaction
retry queue inside the Host Agent
project memory stored in plugin preferences
confidence score treated as authorization
```

## 18. Relationship to OpenTakeoff distillation

`../../docs/domain-packs/architecture/DRAWING_TAKEOFF_LOCAL_ADAPTER.md` records the separate drawing-takeoff binding boundary and the external-reference distillation that motivated several of these engineering checks.

The dependency direction is deliberately absent:

```text
OpenTakeoff code --X--> Revit add-in dependency
OpenTakeoff MCP  --X--> Revit capability identity
OpenTakeoff state --X--> Project Anatomy authority
```

Only generic engineering patterns are reused.

## 19. Acceptance bar before implementation claims

Documentation can be complete while implementation remains absent. A future implementation should not be called implemented until the relevant slice has executable proof.

For the first read-only slice, minimum proof should include:

```text
closed operation registry implemented
manifest derived from that registry
Revit 2027 instance/document observation
one scoped element query
one room/spatial snapshot
one human/Host-Agent parity test
negative stale-context test
conformance suite for exposed operations
no arbitrary-code surface
offline local run
```

For any later model-write slice, add:

```text
exact preflight contract
exact human authorization fixture
named transaction
before/after effect trace
single-use/idempotency proof
rollback or explicit manual-reversal proof
unexpected effects == 0
no save/sync side effect
```

Until those proofs exist, the status remains documented non-implemented or partial according to the actual slice.

## Final rule

```text
One registry declares.
One operation implementation executes.
Human and agent paths prove parity.
Refusal is a first-class technical result.
Corrections preserve the original proposal.
Benchmarks measure engineering quality.
Pantheon still governs admission and decisions.
Revit still executes locally.
```
